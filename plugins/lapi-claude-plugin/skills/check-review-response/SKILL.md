name: check-review-response
description: 自分が過去にレビューしたPRについて、前回指摘以降の対応差分を突き合わせ、指摘が解消されたか・対応で新たな問題が出ていないかをチェックする
---

## 実行フロー

自分が過去にレビューしたPRについて、**前回の自分の指摘への対応を検収する**。全観点のレビューをやり直すものではない。

引数としてPR番号またはPR URLを受け取れる。引数がない場合は現在のブランチに紐づくPRを対象とする。

このスキルを呼び出されたら、以下のステップを順番に実行すること。

---

### ステップ1: 対象PRの特定

- 引数でPR番号/URLが渡された場合: それを対象とする
- 渡されなかった場合: `gh pr view --json number,title,url,headRefName` で現在のブランチに紐づくPRを取得する

特定できなかった場合はAskUserQuestionで対象PRを聞く。

特定したPR（番号とタイトル）を宣言してから次へ進む。

---

### ステップ2: 前回の自分の指摘の復元

自分のGitHubユーザー名を `gh api user --jq .login` で取得する。

対象PRから自分が過去に付けたレビューを取得し、自分が作成したものだけに絞る:

- インラインコメント: `gh api repos/<owner>/<repo>/pulls/<番号>/comments`（`user.login`・`path`・`line`・`body`・`created_at` を見る）
- レビュー本文と提出時刻: `gh api repos/<owner>/<repo>/pulls/<番号>/reviews`（`user.login`・`body`・`submitted_at`・`state` を見る）

あわせて、自分の指摘スレッドへの**著者からの返信**（インラインコメントの `in_reply_to_id` が自分のコメントを指すもの）も取得しておく。ステップ4で「コード変更ではなく返答・反論で対応された」ケースを判定するのに使う。

自分の指摘を1件ずつ番号付きで一覧化し、ユーザーに提示する。指摘が1件も見つからない場合は、その旨を伝えて「前回レビューが特定できないため対応差分の検収ができない」と報告し、必要なら通常の `code-review` を案内して終了する。

自分の**最後の指摘時刻**を対応差分の基準時刻として保持する。これはレビューの `submitted_at` と、自分のインラインコメントの `created_at` の**両方を合わせた最大値**とする（レビューにまとめず単発投稿したコメントは `submitted_at` を持たないため、`created_at` も加味しないと取りこぼす）。

---

### ステップ3: 対応差分の特定

`gh pr view <番号> --json commits` でコミット一覧（`oid`・`committedDate`）を取得する。

基準時刻（ステップ2）より後に積まれたコミット群を「対応分」とみなす。対応差分は次のように切り出す:

- baseline = 基準時刻**以前**の最新コミットの `oid`（＝前回レビュー時点でPRのHEADだったコミット）
- head = 現在のPRのHEADコミットの `oid`
- 対応差分 = baseline から head までの差分。`gh api repos/<owner>/<repo>/compare/<baseline>...<head>` のパッチ、またはローカルにチェックアウト済みなら `git diff <baseline>...<head>` で取得する

基準時刻より後のコミットが存在しない場合は、「前回レビュー以降の対応コミットがない」と報告して終了する。

特定した対応差分の範囲（baseline/head の短縮ハッシュと対象ファイル数）を宣言してから次へ進む。

---

### ステップ4: 指摘の解消チェック（場面A）

ステップ2の各指摘について、対応差分を突き合わせて1件ずつ判定する。判定は次の4段階:

- ✅ 解消済み: 指摘内容が対応差分で適切に修正されている
- ⚠️ 部分対応: 一部だけ直っている／取りこぼしがある（例: 指摘した問題のうち一箇所は直ったが、同じ問題を持つ別の箇所が残っている）
- 💬 別方針・反論で対応: 指摘どおりには直さず、著者が別アプローチで対応した・または反論やコメント返答をしている。**指摘どおりに直っていない事実をニュートラルに示すだけ**にとどめ、その方針が妥当かどうかの評価は行わない（このスキルの責務外）
- ❌ 未着手: 対応差分にも返答にも該当する動きがない

判定の根拠は具体的に書くこと。特に ⚠️ は「何が直り、何が残っているか」を `file:line` 付きで明示する。💬 は著者の対応内容／返答の要点を引用し、元の指摘との差分を示す。指摘が複数の場所に関わる場合は、各場所の対応有無を個別に確認すること（一箇所直っただけで ✅ にしない）。

---

### ステップ5: 対応差分の新規問題チェック（場面B）

対応差分そのものをレビューし、**対応によって新たに混入した問題**を洗い出す。前回指摘の解消とは独立に、この差分が新しく持ち込んだバグ・副作用・デグレを見る。具体的には:

- 指摘を直すために別の呼び出し元・別のケースを壊していないか
- 修正による副作用・想定外の挙動変化・デグレが入っていないか
- 修正差分自体にコードを読むだけでわかるバグがないか

挙げるのは**コードの健全性を明らかに下げているものに限る**（放置するとバグ・機能不全・セキュリティ問題・データ破損・仕様違反を引き起こすもの）。好み・スタイル・些末な改善案・「〜かもしれない」レベルの曖昧なものは挙げない。各指摘には `file:line` を必ず添える。

---

### ステップ6: 結果報告

以下の形式でまとめて報告する。PRへのコメント自動投稿は**しない**（ユーザーが内容を確認してから貼る想定）。

1. **指摘ごとの解消状況**: 指摘番号・概要・判定（✅/⚠️/💬/❌）・根拠を表形式で
2. **対応で新たに出た問題**: ステップ5の指摘リスト（なければ「なし」と明記）
3. **総括**: 再レビューコメントとしてそのまま貼り付けられる文章

全指摘が ✅ で新規問題も1件もない場合は「対応に問題なし」と明確に伝えること。⚠️・❌ が残る、または 💬（指摘どおりに直っていない）が含まれる場合は、確認・判断が必要な点として総括で目立たせること。
