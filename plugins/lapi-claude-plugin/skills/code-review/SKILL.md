## 実行フロー

このスキルを呼び出されたら、以下のステップを順番に実行すること。

---

### ステップ1: レビュー対象の特定

`gh pr view --json number,title,url,headRefName,baseRefName` で現在のブランチに紐づくPRの取得を試みる。

- PRが取得できた場合: そのPRをレビュー対象とする
- PRが取得できなかった場合: `gh repo view --json defaultBranchRef` でデフォルトブランチを取得し、`<defaultBranch>...HEAD` の差分をレビュー対象とする

特定した対象（PR番号とタイトル、または「baseブランチ `<name>` との差分」）をユーザーに宣言してから次へ進む。

---

### ステップ2: 内容取得

レビュー対象の diff、変更ファイル一覧、PR本文（PRがある場合）、既存コメント（PRがある場合）を取得する。

- PRあり: `gh pr diff`, `gh pr view --json body,comments,reviews`
- PRなし: `git diff <defaultBranch>...HEAD`

---

### ステップ3: 観点ごとのレビューagent並列起動

以下6つの観点について、Agentツールで**並列に**レビュー生成agentを起動する（1つのメッセージで複数のAgentツール呼び出しを行う）。

1. **設計**: 変更全体の設計が妥当か。コード同士のインタラクションが意味のあるものか。この変更はこのコードベース／このライブラリに帰属すべきものか。システムの残りの部分とよく統合されているか
2. **機能性**: 開発者が意図した通りに動作するか。エンドユーザーと将来このコードを使う開発者の双方にとって、その挙動はよいものか。エッジケースは考慮されているか。並行性の問題（デッドロック・レースコンディション）が入り込んでいないか。コードを読むだけでわかるバグが存在しないか
3. **複雑さ**: 必要以上に複雑になっていないか。コードの読み手が素早く理解できるか。呼び出したり修正したりするときにバグが入り込みやすい構造になっていないか。オーバーエンジニアリング（過剰な一般化、現在は不要な機能の追加、将来の問題への先回り）になっていないか。
4. **テスト**: 変更に対して適切なユニットテスト・インテグレーションテスト・E2Eテストが含まれているか。テストは正しく・意味があり・役に立つものか。コードが壊れたときに実際に失敗するか。フォールス・ポジティブを示さないか。各アサーションはシンプルで役に立つか。テストは適切に分離されているか。テストにも不必要な複雑さが入り込んでいないか
5. **命名**: あらゆるものによい名前が選ばれているか。その要素が何であるか・何をするものであるかを完全に伝えており、かつ読むのが難しくなるほど長すぎない、適切な長さの名前になっているか
6. **コメント**: 明確なコメントが書かれているか。すべてのコメントは実際に必要なものか。コメントは「なぜそのコードが存在するのか（why）」を説明しているか。「コードが何をしているのか（what）」を説明するコメントになっていないか（その場合はコード自体をシンプルにすべき。ただし正規表現や複雑なアルゴリズムは例外）。決定の背後にある理由など、コード自体に含めるのが困難な情報を補っているか。なお、クラス・モジュール・関数のドキュメント（目的・使い方・挙動の説明）はコメントとは別物として扱う

各agentには以下を渡す:

- diff全文
- PR本文（あれば）
- 担当する観点とその定義
- 出力形式: 各コメントについて `{file, line, message}` の構造化リスト

各agentは自分の観点に絞ってインラインコメント案を返す。対応の必要性があるもののみを出力させ、任意改善・好み・参考情報レベルの指摘は出力しないこと。

---

### ステップ4: 横断検証agent

ステップ3で集めた全コメント案を1つの検証agentに渡す。

検証agentの唯一の判断基準は、以下のコードレビュー原則である:

> 一般に、ある変更が作業対象のシステムのコード全体の健全性を具体的に向上させる状態に一度でも達したならば、たとえその変更が完璧なものでなくても、レビュアは承認を賛成しなければならない。

各コメントについて「そのコメントが指摘している事項が、コード全体の健全性の向上に関わるものか」を評価する。健全性の向上に関わるものは採用、関わらないもの（完璧主義、好み、些末な改善案など）は除外する。他の基準は用いない。

検証agentは各コメントについて「採用 / 除外」と理由を返す。除外されたコメントは静かに捨て、件数だけ後で参考表示する。

---

### ステップ5: 結果の提示

検証を通過したコメントを以下の形式で整理して表示する。

- ファイル順 or 観点順で整理
- 各コメントは `file:line` のmarkdownリンク形式で示す
- 末尾に検証で除外された件数を参考表示

---

### ステップ6: PR投稿（PRがある場合のみ）

ステップ5の後、PRがある場合に限り、ユーザーに投稿の意向を確認する。PRがない場合（base差分レビュー）はステップ5で終了する。

- AskUserQuestionで投稿するかどうかをユーザーに確認する
- 投稿する場合、採用するコメントの絞り込み（全採用 / 一部選択 / 編集）をユーザーから受け取る
- `gh pr review --comment` でインラインコメントを送信する
- 投稿後、PRのURLを報告する

---

## 注意事項

- ステップ3のレビューagentは必ず**並列起動**する（1メッセージで複数 Agent ツール呼び出し）
- 検証で除外されたコメントは「件数のみ」表示し、内容は出さない
- インラインコメントの行番号は diff の右側（追加・変更後）の行を基準にする
- ユーザーへの質問はAskUserQuestionツールを使う
