name: code-review
description: 観点ごとのレビューエージェントを並列起動し、横断検証を経てPRまたはbase差分をレビューする
---

## 実行フロー

このスキルを呼び出されたら、以下のステップを順番に実行すること。

---

### ステップ1: レビュー対象の特定

`gh pr view --json number,title,url,headRefName,baseRefName` で現在のブランチに紐づくPRの取得を試みる。

- PRが取得できた場合: そのPRをレビュー対象とする
- PRが取得できなかった場合: `gh repo view --json defaultBranchRef` でデフォルトブランチを取得し、`<defaultBranch>...HEAD` の差分をレビュー対象とする

特定した対象（PR番号とタイトル、または「baseブランチ `<name>` との差分」）をユーザーに宣言してから次へ進む。

---

### ステップ2: 内容取得

レビュー対象の diff、変更ファイル一覧、PR本文（PRがある場合）、既存コメント（PRがある場合）を取得する。

- PRあり: `gh pr diff`, `gh pr view --json body,comments,reviews`
- PRなし: `git diff <defaultBranch>...HEAD`

---

### ステップ3: 観点ごとのレビューagent並列起動

以下6つの観点について、Agentツールで**並列に**レビュー生成agentを起動する（1つのメッセージで複数のAgentツール呼び出しを行う）。

1. **設計**: 変更全体の設計が妥当か。コード同士のインタラクションが意味のあるものか。この変更はこのコードベース／このライブラリに帰属すべきものか。システムの残りの部分とよく統合されているか
2. **機能性**: 開発者が意図した通りに動作するか。エンドユーザーと将来このコードを使う開発者の双方にとって、その挙動はよいものか。エッジケースは考慮されているか。並行性の問題（デッドロック・レースコンディション）が入り込んでいないか。コードを読むだけでわかるバグが存在しないか
3. **複雑さ**: 必要以上に複雑になっていないか。コードの読み手が素早く理解できるか。呼び出したり修正したりするときにバグが入り込みやすい構造になっていないか。オーバーエンジニアリング（過剰な一般化、現在は不要な機能の追加、将来の問題への先回り）になっていないか。
4. **テスト**: 変更に対して適切なユニットテスト・インテグレーションテスト・E2Eテストが含まれているか。テストは正しく・意味があり・役に立つものか。コードが壊れたときに実際に失敗するか。フォールス・ポジティブを示さないか。各アサーションはシンプルで役に立つか。テストは適切に分離されているか。テストにも不必要な複雑さが入り込んでいないか
5. **命名**: あらゆるものによい名前が選ばれているか。その要素が何であるか・何をするものであるかを完全に伝えており、かつ読むのが難しくなるほど長すぎない、適切な長さの名前になっているか
6. **コメント**: 明確なコメントが書かれているか。すべてのコメントは実際に必要なものか。コメントは「なぜそのコードが存在するのか（why）」を説明しているか。「コードが何をしているのか（what）」を説明するコメントになっていないか（その場合はコード自体をシンプルにすべき。ただし正規表現や複雑なアルゴリズムは例外）。決定の背後にある理由など、コード自体に含めるのが困難な情報を補っているか。なお、クラス・モジュール・関数のドキュメント（目的・使い方・挙動の説明）はコメントとは別物として扱う

各agentには以下を渡す:

- diff全文
- PR本文（あれば）
- 担当する観点とその定義
- レビュー対象（PR番号とタイトル、またはbase差分の説明）

各agentへの指示:

- 自分の観点に絞ってインラインコメント案をテキストで返すこと
- **コードの健全性を明らかに下げているもののみを候補として挙げること**。具体的には、放置するとバグ・機能不全・セキュリティ問題・データ破損・仕様違反・明らかな複雑化・明らかなテスト不足・明らかに不適切な命名やコメントを引き起こすものに限る
- 以下に該当するものは指摘しないこと:
  - 好み・スタイルの問題・完璧主義・些末な改善案・別解の提示・参考情報レベルのもの
  - 渡されたコンテキスト（diff・PR本文）から問題と断定できない、曖昧なもの・「〜かもしれない」「〜の恐れがある」のように可能性ベースで書かざるを得ないもの
- 各コメントには対応する `file:line` と担当観点名を必ず含めること
- `message` は **PRインラインコメントとしてそのまま貼り付けて使える文章** で書くこと。具体的には:
  - 何が問題か（現状の挙動・コードの状態）を明示する
  - なぜそれが健全性を下げるのか（影響・リスク）を説明する
  - 可能なら修正の方向性を簡潔に添える
  - 読み手はPR作者であり、トーンは丁寧かつ建設的。冗長な前置きや謝辞は不要
  - 必要に応じてコードブロック（` ``` `）や該当箇所の引用を含めてよい
- 出力形式: コメントごとに `{viewpoint, file, line, message}` の構造化リスト（YAML/JSONなど親agentがパースしやすい形式）。`message` は複数行のmarkdownでよい

---

### ステップ4: 横断検証agent

ステップ3で集めた全コメント案を1つの検証agentに渡す。

検証agentの唯一の判断基準は、以下のコードレビュー原則である:

> 一般に、ある変更が作業対象のシステムのコード全体の健全性を具体的に向上させる状態に一度でも達したならば、たとえその変更が完璧なものでなくても、レビュアは承認を賛成しなければならない。

すべてのコメントについて「そのコメントが指摘している事項が、コード全体の健全性を明らかに下げているか」を再評価する。明らかに下げていると断定できないものはすべて除外する。特に以下に該当するものは除外すること:

- 好み・スタイル・完璧主義・些末な改善案・別解の提示・参考情報レベルの指摘
- コンテキストが不足しており、問題であると断定できない曖昧な指摘（「〜かもしれない」「〜の恐れがある」「もし〜なら問題」など、確証なく可能性ベースで書かれているもの）

指摘の根拠が diff および渡された文脈から確実に読み取れ、かつコードの健全性を明らかに下げていると断定できる場合のみ採用すること。

**機能性の観点のコメントについては追加の検証を課す**: 「その挙動が本当に誤っている」ことを、e2eテストまたはブラウザテストを実際に実行して確認すること。コードを読んだだけの推論で「動作がおかしいはず」と判断せず、可能な限り実際にテストを動かして再現・確認する。

- 既存のe2eテスト・ブラウザテストで確認できる場合はそれを実行する。確認に適したテストが無い場合は、その挙動を再現する最小限のe2eテスト／ブラウザテストを書いて実行し、誤動作を確認する
- テストを実行して誤動作が再現・確認できた機能性コメントは採用し、どのテストで確認したか（実行したテスト名・コマンドと結果の要旨）を判定理由に含める
- テストを実行したが誤動作を再現できなかった機能性コメントは除外する
- 確認手段を用意できなかった（実行できる適切なテストが無く、テストを書くことも困難だった）機能性コメントは**除外せず採用として残す**。ただしコメント本文の冒頭に「テストによる再現確認ができていない」旨を明示し、判定理由にも確認手段を用意できなかった理由を記載すること

検証agentは各コメントについて「採用 / 除外」と理由を判定し、採用コメントの構造化リストと除外件数を返す。

---

### ステップ5: 結果の提示

検証を通過したコメントを、**そのままPRインラインコメントとして使える形** で表示する。一覧の要約として短く書くのではなく、各コメントの本文をPR投稿時と同じ完全な形（問題の説明・影響・修正方針）で記載すること。

形式:

- ファイル順に並べる
- 各コメントは以下の構造で記載する
  - 見出し: `### [<viewpoint>] <file>:<line>` （file:lineはmarkdownリンク形式）
  - 本文: レビューagentが生成した `message` をそのまま掲載（複数行・コードブロック可）
- 末尾に検証で除外された件数を参考表示する

例:

```
### [機能性] [src/foo.ts:42](src/foo.ts#L42)

`user` が null の場合にここで `user.name` を参照しており、ランタイムでクラッシュします。
直前の `findUser` は見つからない場合 null を返すため、以下のように早期returnを入れるのが安全です:

​```ts
const user = findUser(id);
if (user === null) return;
​```

### [命名] [src/bar.ts:108](src/bar.ts#L108)

関数名 `process` が役割を表していません。この関数は実際には「請求書の検証と正規化」を行っているため、`normalizeInvoice` などの具体的な名前にするとコールサイトの意図が読み取りやすくなります。

### [テスト] [src/baz.ts:200](src/baz.ts#L200)

エラーパス（`fetchOrder` が失敗した場合）に対するアサーションが追加されていません。今回の変更で新たに分岐が増えているため、失敗系の挙動が壊れた際に検知できなくなっています。`it('returns null when fetch fails', ...)` のようなケースを追加してください。

---
検証で除外: 3件
```

### ステップ6: PR投稿または自己修正（PRがある場合のみ）

ステップ5の後、PRがある場合に限り以下を確認する。PRがない場合（base差分レビュー）はステップ5で終了する。

まず `gh pr view <番号> --json author --jq .author.login` でPR作者のGitHubログインを取得し、`gh api user --jq .login` で取得した自分のログインと比較する。

- **作者が自分自身の場合**: 後述の「ステップ6-A: 自己修正」を実行する
- **作者が自分以外の場合**: 後述の「ステップ6-B: PR投稿」を実行する

---

#### ステップ6-A: 自己修正（作者が自分自身の場合）

検証を通過したコメントの指摘内容を、ワーキングツリー上で実際に修正する。

- 各コメントについて、指摘された問題を解消する修正をファイルに適用する
- 「テストによる再現確認ができていない」旨が付いた機能性コメントなど、修正の妥当性が不確実なものは無理に修正せず、その旨を理由とともに報告する
- **コミットは行わない**。ワーキングツリーへの変更適用までにとどめる
- 修正完了後、コメントごとに「どのファイルにどういう修正を行ったか（または修正を見送ったか）」を簡潔に提示する。修正内容は対象 `file:line`・変更の要旨・対応するレビュー観点がわかる形でまとめる

---

#### ステップ6-B: PR投稿（作者が自分以外の場合）

ユーザー承認は不要。全コメントをpending review（下書き）としてGitHubに追加する。

- commit SHA を取得する:

  ```bash
  gh pr view <番号> --json headRefOid --jq .headRefOid
  ```

- 全コメントを1つのpending review（下書き）としてまとめて追加する。**`event` フィールドは絶対に指定しないこと**（指定するとCOMMENT/APPROVE/REQUEST_CHANGESとして即公開されてしまう。指定なしにすることでpending下書きになる）:

  ```bash
  gh api repos/{owner}/{repo}/pulls/<番号>/reviews \
    -X POST \
    -f commit_id='<SHA>' \
    -f body='' \
    -f 'comments[][path]=<file>' \
    -F 'comments[][line]=<行番号>' \
    -f 'comments[][body]=[<viewpoint>] 本文' \
    -f 'comments[][side]=RIGHT'
  ```

- 行番号は diff の右側（追加・変更後）かつ diffハンク内の行を指定する
- diff外のファイル・行を指す指摘は `comments` から除外し、review の `body` にまとめて記載する
- 追加完了後、pending reviewとして保存された旨とPRのURLを報告する

---

## 注意事項

- ステップ3のレビューagentは必ず**並列起動**する（1メッセージで複数 Agent ツール呼び出し）
- 検証で除外されたコメントは「件数のみ」表示し、内容は出さない
- インラインコメントの行番号は diff の右側（追加・変更後）の行を基準にする
- ユーザーへの質問はAskUserQuestionツールを使う
