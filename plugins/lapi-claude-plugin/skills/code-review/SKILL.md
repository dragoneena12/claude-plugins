## 実行フロー

このスキルを呼び出されたら、以下のステップを順番に実行すること。

---

### ステップ1: レビュー対象の特定

`gh pr view --json number,title,url,headRefName,baseRefName` で現在のブランチに紐づくPRの取得を試みる。

- PRが取得できた場合: そのPRをレビュー対象とする
- PRが取得できなかった場合: `gh repo view --json defaultBranchRef` でデフォルトブランチを取得し、`<defaultBranch>...HEAD` の差分をレビュー対象とする

特定した対象（PR番号とタイトル、または「baseブランチ `<name>` との差分」）をユーザーに宣言してから次へ進む。

---

### ステップ2: 内容取得

レビュー対象の diff、変更ファイル一覧、PR本文（PRがある場合）、既存コメント（PRがある場合）を取得する。

- PRあり: `gh pr diff`, `gh pr view --json body,comments,reviews`
- PRなし: `git diff <defaultBranch>...HEAD`

---

### ステップ3: 観点ごとのレビューagent並列起動

`mktemp -d -t code-review.XXXXXX` を実行して出力ディレクトリを作成し、得られたパスを `<review_dir>` として以降のステップで使い回す。

以下6つの観点について、Agentツールで**並列に**レビュー生成agentを起動する（1つのメッセージで複数のAgentツール呼び出しを行う）。各観点には対応する出力ファイル名（英語）を定めている。

1. **設計** (`design`): 変更全体の設計が妥当か。コード同士のインタラクションが意味のあるものか。この変更はこのコードベース／このライブラリに帰属すべきものか。システムの残りの部分とよく統合されているか
2. **機能性** (`functionality`): 開発者が意図した通りに動作するか。エンドユーザーと将来このコードを使う開発者の双方にとって、その挙動はよいものか。エッジケースは考慮されているか。並行性の問題（デッドロック・レースコンディション）が入り込んでいないか。コードを読むだけでわかるバグが存在しないか
3. **複雑さ** (`complexity`): 必要以上に複雑になっていないか。コードの読み手が素早く理解できるか。呼び出したり修正したりするときにバグが入り込みやすい構造になっていないか。オーバーエンジニアリング（過剰な一般化、現在は不要な機能の追加、将来の問題への先回り）になっていないか。
4. **テスト** (`testing`): 変更に対して適切なユニットテスト・インテグレーションテスト・E2Eテストが含まれているか。テストは正しく・意味があり・役に立つものか。コードが壊れたときに実際に失敗するか。フォールス・ポジティブを示さないか。各アサーションはシンプルで役に立つか。テストは適切に分離されているか。テストにも不必要な複雑さが入り込んでいないか
5. **命名** (`naming`): あらゆるものによい名前が選ばれているか。その要素が何であるか・何をするものであるかを完全に伝えており、かつ読むのが難しくなるほど長すぎない、適切な長さの名前になっているか
6. **コメント** (`comments`): 明確なコメントが書かれているか。すべてのコメントは実際に必要なものか。コメントは「なぜそのコードが存在するのか（why）」を説明しているか。「コードが何をしているのか（what）」を説明するコメントになっていないか（その場合はコード自体をシンプルにすべき。ただし正規表現や複雑なアルゴリズムは例外）。決定の背後にある理由など、コード自体に含めるのが困難な情報を補っているか。なお、クラス・モジュール・関数のドキュメント（目的・使い方・挙動の説明）はコメントとは別物として扱う

各agentには以下を渡す:

- diff全文
- PR本文（あれば）
- 担当する観点とその定義
- レビュー対象（PR番号とタイトル、またはbase差分の説明）
- テンプレートファイルのパス: `{plugin_root}/skills/code-review/templates/review-output.md`
- 出力先ファイルパス: `<review_dir>/<viewpoint_slug>.md` （例: 設計 → `<review_dir>/design.md`）

各agentへの指示:

- テンプレートファイルを読み、その形式に従ってレビュー結果ファイルを Write ツールで作成すること
- 自分の観点に絞って、各コメントを以下3優先度のいずれかに分類すること
  - **must**: マージ前に必ず修正すべき問題（バグ・機能不全・セキュリティ問題・データ破損リスク・仕様違反など）
  - **should**: コード全体の健全性向上に明確に寄与する指摘
  - **suggest**: 必須ではない改善提案・別解の提示・参考情報
- 各コメントには対応する `file:line` と「観点」名を明記すること
- 該当するコメントが無いセクションは「（なし）」とすること
- テキストでは返答せず、ファイル書き込みのみ行うこと（最後に出力ファイルパスを1行返すだけでよい）

---

### ステップ4: 横断検証agent

`<review_dir>` 配下の全6ファイルを検証agentに渡す。

検証agentの唯一の判断基準は、以下のコードレビュー原則である:

> 一般に、ある変更が作業対象のシステムのコード全体の健全性を具体的に向上させる状態に一度でも達したならば、たとえその変更が完璧なものでなくても、レビュアは承認を賛成しなければならない。

優先度（must / should / suggest）にかかわらず、すべてのコメントについて「そのコメントが指摘している事項が、コード全体の健全性の向上に具体的に寄与するものか」を同じ基準で再評価する。寄与しないものは優先度に関係なく除外する。特に以下に該当するものはすべて除外すること:

- 参考程度・好み・完璧主義・些末な改善案・無意味な指摘
- コンテキストが不足しており、問題であると断定できない「可能性のみ」の指摘（例: 「〜かもしれない」「〜の恐れがある」「もし〜なら問題」など、確証なく憶測で書かれているもの）

レビューagent側が `suggest` に分類していたとしても、健全性の向上に具体的に寄与しないなら容赦なく除外する。指摘の根拠が diff および渡された文脈から確実に読み取れる場合のみ採用すること。

検証agentは各コメントについて「採用 / 除外」と理由を判定し、採用されたコメントだけを残した統合ファイル `<review_dir>/_merged.md` を作成する。統合ファイルは優先度（must → should → suggest）の順に並べ、各コメント内で観点・file:line を明示する。除外件数も末尾に記載する。

---

### ステップ5: 結果の提示

ユーザーに以下を提示する。コメント本文を本文中に展開してはならない。

- 統合ファイルの絶対パス: `<review_dir>/_merged.md`
- 各レビューagentが生成した観点別ファイルの絶対パス一覧（`<review_dir>/design.md` など6件）
- サマリ: 採用件数（must / should / suggest それぞれの件数）と、検証で除外された件数

例:

```
レビュー結果ファイル:
- 統合: /tmp/code-review.XXXXXX/_merged.md
- 観点別:
  - /tmp/code-review.XXXXXX/design.md
  - /tmp/code-review.XXXXXX/functionality.md
  - /tmp/code-review.XXXXXX/complexity.md
  - /tmp/code-review.XXXXXX/testing.md
  - /tmp/code-review.XXXXXX/naming.md
  - /tmp/code-review.XXXXXX/comments.md

採用: must 2件 / should 5件 / suggest 1件
検証で除外: 3件
```

---

### ステップ6: PR投稿（PRがある場合のみ）

ステップ5の後、PRがある場合に限り、ユーザーに投稿の意向を確認する。PRがない場合（base差分レビュー）はステップ5で終了する。

- AskUserQuestionで投稿するかどうかをユーザーに確認する
- 投稿する場合、採用するコメントの絞り込み（全採用 / 一部選択 / 編集）をユーザーから受け取る
- `gh pr review --comment` でインラインコメントを送信する。各コメント本文の先頭に `[<priority>][<viewpoint>]` のプレフィックスを付ける（例: `[must][機能性] ここでnullチェックが…`）
- 投稿後、PRのURLを報告する

---

## 注意事項

- ステップ3のレビューagentは必ず**並列起動**する（1メッセージで複数 Agent ツール呼び出し）
- 各レビューagentはテンプレートを参照したファイル出力のみを行い、テキストで指摘内容を返さない
- 検証で除外されたコメントは「件数のみ」表示し、内容は出さない
- インラインコメントの行番号は diff の右側（追加・変更後）の行を基準にする
- ユーザーへの質問はAskUserQuestionツールを使う
