## いつ使うか

レビューで検出した指摘（観点・対象箇所・問題の要旨）を、そのままPRインラインコメントとして貼れる本文に書き起こすとき。「何を指摘するか」は呼び出し元が決め、本スキルは「どう書くか」を担う。

## 入力

指摘ごとに以下を受け取る。

- 対象 `file:line`
- 指摘の要旨（何が・なぜ問題か）

## 実行フロー

各指摘について、下記の作法に従って `message`（PRインラインコメント本文）を書き起こし、`{file, line, message}` の構造化リストで返す。

> **最も重要: できる限り短く書く。** 下記の要素を満たしたうえで、余分な語を削り、最小限の文量で伝える。短さと詳しさが競合する場合は短さを優先する。

### コメントに必ず含める要素

- **何が問題か**: 現状の挙動・コードの状態を明示する
- **なぜ問題か**: それがコードの健全性をどう下げるのか（影響・リスク）を説明する。必要ならベストプラクティスや根拠を添える
- **修正の方向性**: 可能なら簡潔に添える。ただし最終的な修正の判断・実装は作者に委ねる

### 書き方の原則

- **コードについて述べ、書き手個人について述べない**。「あなたは〜し忘れている」ではなく「このコードは〜」。対象は常にコードであり、人ではない
- **指摘と方向性のバランスを取る**。何が問題かを明確にしたうえで、どう直すかは作者の裁量に委ねる姿勢で書く。ただし具体的な修正例を示すことで理解が早まる場合は、コード例（コードブロック）を添えてよい
- **理解しづらいコード自体が問題なら、簡素化や説明コメントの追加を促す**。「意図を説明してほしい」で終わらせない。レビュー上のやり取りは将来コードを読む人には残らないため、コードやコード内コメントを改善する方向へ導く
- **トーンは丁寧かつ建設的に**。読み手はPR作者。冗長な前置きや謝辞は不要

### フォーマット

- そのままPRインラインコメントとして貼り付けて使える文章にする
- 必要に応じてコードブロック（` ``` `）や該当箇所の引用を含めてよい
