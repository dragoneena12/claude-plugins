# Explain Diff

指定されたコード変更について、リッチでインタラクティブな解説を作成すること。

以下のセクションで構成する。

- **Background（背景）**: この変更に関連する既存システムを説明する（そのために周辺コードを幅広く探索すること）。読者がどこまで知っているか分からないので、初心者向けの深い背景説明を含める（すでに詳しい読者はスキップできる旨を明記する）。そのうえで、変更に直接関係するより絞り込んだ背景を続ける。
- **Intuition（直観）**: このコード変更の核となる直観を説明する。ここでの焦点は本質を伝えることであり、詳細を網羅することではない。トイデータを使った具体例を用いること。図やダイアグラムを惜しみなく使うこと。
- **Code（コード）**: コード変更のハイレベルなウォークスルーを行う。変更を理解しやすい単位でグループ化・順序付けすること。
- **Quiz（クイズ）**: このPRの理解度を試す問題を5問作成する。難易度は中程度とし、PRの中身を実際に理解していないと答えられない程度に難しく、しかし引っかけ問題にはしないこと。目的は、読者が本当に理解できたかを自分で確認できるようにすることである。インタラクティブな多肢選択問題として提示し、選択肢をクリックすると正誤とフィードバックが表示されるようにする。

## フォーマット

- CSSとJavaScriptを含んだ、自己完結した単一のHTMLファイルとして出力する。全体をセクション見出しと目次を備えた1枚の長いページにすること。トップレベルの構造にタブを使わないこと。スマートフォンでも閲覧できる程度の基本的なレスポンシブスタイルがあるとよい。ファイルはコードリポジトリの外のグローバルな場所に置き、ファイル名は必ず今日の日付の `YYYY-MM-DD-` 形式で始めること。時系列で整理でき、バージョン管理の対象外に保てるためである。例: `/tmp/2026-01-12-explanation-<slug>.html`
- Martin Kleppmannのような明快さと流れのある文章で、classic styleで魅力的に書くこと。セクション間の遷移は滑らかにすること。
- ダイアグラムに関するヒント:
  - 理想的には、少数のダイアグラムファミリーを選び、解説全体を通して様々なケースの説明に再利用すること。有用なダイアグラムの種類:
    - UIの変更を説明するための、ユーザーがアプリで目にするUIの非常に簡略化したバージョン。
    - コンポーネント間のデータフローや通信を示すシステム図。ここには必ずサンプルデータを含めること！
  - ASCIIアートの図は使わないこと。ダイアグラムは常にシンプルなHTMLデザインで描き、物事の列挙にはHTMLのリストを使うこと。
  - コードブロックには常に `<pre>` タグを使うこと。代わりにカスタムスタイルのdivを使う場合は、CSSに **必ず** `white-space: pre-wrap` を指定すること。さもないとブラウザがすべての改行を1行に潰してしまう。ファイルを保存する前に、HTMLソース内の各コードブロックを確認し、そのCSSに `white-space: pre` または `pre-wrap` が含まれていることを検証すること。
- 重要な概念や定義、重要なエッジケースなどにはコールアウトを使うこと。
