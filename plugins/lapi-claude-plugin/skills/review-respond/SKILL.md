## 実行フロー

自分が作者のPRに付いたレビューコメントへの対応を、トリアージ→修正→push→返信→再レビュー依頼まで一気通貫で行う。

ユーザーの確認ポイントは3箇所（対応コメントの取捨選択・コミット前の差分確認・返信文面の確認）。それ以外は自動で進める。確認にはAskUserQuestionを使わないこと。提示内容をターン最後のテキストメッセージとして出力してターンを終え、番号や自由記述で回答してもらう（後ろにツール呼び出しが続くテキストはUI上で要約され、ユーザーに全文が見えないため）。

このスキルを呼び出されたら、以下のステップを順番に実行すること。

---

### ステップ1: 対象PRの特定

`gh pr view --json number,title,url,author,headRefName,state` で現在のブランチに紐づくPRを取得する。引数でPR番号/URLが渡された場合はそれを優先する。

- PRが見つからない場合: その旨を報告して終了する
- PRの作者が自分（`gh api user --jq .login`）でない場合: このスキルは作者としてのレビュー対応用であることを伝え、続行するか確認する
- マージ済み/クローズ済みの場合: その旨を報告して終了する

特定したPR（番号とタイトル）を宣言してから次へ進む。

---

### ステップ2: 未対応コメントの収集

自分以外のユーザーによるフィードバックを3系統すべてから収集する。片方だけでは見落とすため、必ず全系統をチェックする。

1. **インラインコメント**: GraphQLで `reviewThreads` を取得し、`isResolved == false` のスレッドだけを対象とする。各スレッドの最後の発言者が自分の場合（＝返信済みで相手の反応待ち）は対象から外す。

   ```bash
   gh api graphql -f query='
   query {
     repository(owner: "<owner>", name: "<repo>") {
       pullRequest(number: <番号>) {
         reviewThreads(first: 100) {
           nodes {
             isResolved
             path
             line
             comments(first: 30) {
               nodes { id databaseId author { login __typename } body createdAt }
             }
           }
         }
       }
     }
   }'
   ```

2. **レビュー本文**: `gh api repos/<owner>/<repo>/pulls/<番号>/reviews` の `body` が空でないもの。`CHANGES_REQUESTED` は必ず、`COMMENTED` は本文に指摘・依頼・質問が含まれるものを対象とする。`APPROVED` のみ（追加指摘なし）は対象外。

3. **issueコメント形式のレビュー**: `gh api repos/<owner>/<repo>/issues/<番号>/comments` のうち、実質的なレビュー内容（指摘・修正依頼・質問）を含むもの。正式なレビューAPIを介さず通常コメントで指摘するレビュアーがいるため、この系統を省略しない。自分の最終アクティビティ（最新コミット、または自分の最終コメントの遅い方）より後のものを対象とする。

botによるコメントも収集するが、人間のレビューと区別できるようマークしておく。未対応コメントが1件もなければ、その旨を報告して終了する。

---

### ステップ3: トリアージと取捨選択（確認ポイント1）

各コメントについて指摘対象のコードを実際に読み、以下の3分類でトリアージする。

- **必須対応**: バグ・セキュリティ問題・仕様違反など、放置すべきでない明確な問題の指摘
- **対応推奨**: 対応する価値のある改善提案。判断の余地があるもの
- **返信のみで良い**: 質問・確認・好みの問題など、コード変更が不要と思われるもの

番号付き一覧として提示する。各コメントには以下を添える:

- コメントの要約と場所（`file:line`）、コメント主
- 分類とその根拠
- 具体的な対応方針案（修正するなら何をどう直すか、返信のみなら返答の方向性）

一覧の提示でターンを終え、どのコメントに修正対応するかを番号で回答してもらう。分類はあくまで提案であり、ユーザーは自由に上書きできる（必須対応の見送り・返信のみからの昇格も可）。選ばれなかったコメントは「返信のみ」として扱う。

---

### ステップ4: 修正の実装と差分確認（確認ポイント2）

選ばれたコメントに対して修正を実装する。**この段階ではコミットしない。**

- 指摘の意図に沿った最小限の修正にとどめ、指摘と無関係なリファクタリングを混ぜない
- 同じ問題が指摘箇所以外にもある場合（同種の誤りの横展開）は、修正したうえで報告に含める
- プロジェクトにテスト・lintの実行手段があれば修正後に実行し、結果を報告に含める

全修正が終わったら、コメントごとに「何をどう直したか」を差分の要点とともに提示し、ユーザーの確認を得る。修正指示があれば反映して再提示する。技術的に対応が困難・不適切と判明したコメントがあれば、この時点で理由とともに「返信のみ」への変更を提案する。

---

### ステップ5: コミット & push

OKが出たらコミットしてpushする。

- コミットメッセージはレビュー対応であることがわかる内容にする（対応した指摘の要約を含める）
- 修正内容が論理的に独立している場合は分割コミットしてよい
- push後、返信で参照するためコミットハッシュを控えておく

---

### ステップ6: 返信案の提示（確認ポイント3）

各コメント（修正対応・返信のみの両方）への返信案を一覧提示する。作者側の返信として以下の作法に従う:

- **修正対応したもの**: 何をどう直したかを簡潔に説明し、対応コミットのハッシュを添える（push済みのコミットはハッシュを書くだけでGitHub上でリンクになる）
- **見送ったもの**: 見送りの理由・背景を丁寧に説明する。指摘自体への感謝や妥当性の認識を示したうえで、判断の根拠を述べる。断定的・防御的な書き方をしない
- **質問への回答**: 質問に正面から答える。設計意図や経緯など、コードから読み取れない文脈を補う
- レビュアーへの感謝は不自然にならない範囲で示す。全コメントに定型文を機械的に付けない

文面はユーザーが確認し、修正指示があれば反映して再提示する。

---

### ステップ7: 返信投稿 & 再レビュー依頼

OKが出たら以下を実行する。

1. **返信の投稿**: インラインコメントへの返信はスレッドへのリプライとして投稿する。

   ```bash
   gh api repos/<owner>/<repo>/pulls/<番号>/comments/<コメントのdatabaseId>/replies -f body='<返信本文>'
   ```

   レビュー本文・issueコメント形式の指摘への返信は、どの指摘への返答か特定できる形（引用やメンション）でissueコメントとして投稿する（`gh pr comment`）。

2. **スレッドのresolve**: 自分ではresolveしない。解消の判断はレビュアーに委ねる。

3. **再レビュー依頼**: コメントを付けたレビュアー（botを除く）に再レビューをリクエストする。

   ```bash
   gh api -X POST repos/<owner>/<repo>/pulls/<番号>/requested_reviewers -f 'reviewers[]=<login>'
   ```

   自分の返信にしか反応していないレビュアーなど、依頼が不自然な相手は対象から外してよい。

---

### ステップ8: 完了報告

以下をまとめて報告する。

- 修正対応したコメント数と要点
- 返信のみで済ませたコメント数
- pushしたコミット
- 再レビューを依頼したレビュアー

---

## 注意事項

- レビュアー側の検収は [check-review-response](../check-review-response)、レビューの実施は [code-review](../code-review) の責務であり、このスキルでは行わない
- ユーザーの確認を得る前に、コミット・push・コメント投稿・再レビュー依頼を実行しない
- 差分確認（ステップ4）や返信確認（ステップ6）でユーザーが中断を選んだ場合は、そこまでの状態（実装済みの修正はワーキングツリーに残る等)を明示して終了する
